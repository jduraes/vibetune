# Clean-room PT3 engine — postmortem (archived)

This folder holds the **abandoned** clean-room ProTracker 3 playback engine and
its analysis scripts. It is kept for posterity. **None of it is in the build.**
The shipping player uses the S.V. Bulba PT2/PT3 player extracted from RomWBW
`tune.asm` (`pt3bulba.inc` + `pt3bulba_shim.inc`).

## What we tried

A from-scratch PT3 decoder, written against `PT3FormatSpec.md`:

| File | Role |
|------|------|
| `pt3engine.inc` | Pattern/position sequencer, per-channel decode, AY flush |
| `pt3chregs.inc` | Per-channel register computation (note/sample/ornament → AY regs) |
| `pt3notetables.inc` | Precomputed note period tables (generated by `Build-Pt3NoteTable.py`) |
| `pt3notes.inc` | Note name/period helpers |
| `Build-Pt3NoteTable.py` | Generates the note-period tables |
| `Check-Pt3Pattern.ps1`, `Dump-Pt3*.ps1` | Offline PT3 structure analysis for `rl2wof.pt3` |

Span: builds **v0.0.72 – v0.0.80**.

## Why it was abandoned

It never reached audible parity with `tune.com` on real hardware. The symptom
set kept rotating (instant return, machine-gun noise, silence, pops) faster than
root causes could be nailed, because a clean-room engine reproduces *all* of the
PT3 format's subtlety (packing, ornaments, envelopes, special commands) at once.
Switching to the proven Bulba player (v0.0.81) removed the decode unknowns and
let us focus on the host integration (ports, timing, COM layout), which is where
the real shipping bugs turned out to be.

## Concrete bugs found (keep these lessons)

1. **Stack leak → instant return to CCP (v0.0.72/0.0.73).**
   `PT3_BIND_PATTERN` left a stray `PUSH AF` with no matching `POP`, so the
   first `RET` unwound into garbage and the program returned to CCP immediately.
   Lesson: balance push/pop per path; a "silent instant exit" is almost always a
   stack imbalance, not a logic bug.

2. **Wrong pattern bind, oscillated twice (v0.0.79/0.0.80).**
   The PT3 pattern table entry is a set of **three consecutive 16-bit words**
   (A/B/C stream pointers). We first read them as header-relative offsets
   (→ silence + pops), "fixed" it to the wrong model, then settled on three
   consecutive table words. For `rl2wof.pt3` position 0 the correct stream
   starts were 68 / 106 / 175. Lesson: validate bind offsets against a hex dump
   of a *known* tune before trusting decode output.

3. **CHREGS register mapping errors (v0.0.78).**
   Sample lines are **4 bytes**, not the assumed width, and channel **volume
   comes from byte C, not byte B**. Wrong widths desynced the whole channel
   stream. Lesson: the per-row byte layout is unforgiving; one wrong stride
   corrupts everything downstream.

4. **AY output policy self-inflicted noise.**
   Early mute/flush wrote 0 to tone-period registers (period 0 = highest pitch),
   causing the constant high whine and pops. This lesson **carried over** to the
   Bulba path and informs the current audio policy (mixer-only pause `reg7=$3F`,
   ROUT-only mute, exit-mute gated on `PSG_TOUCHED`).

## If anyone revisits a clean-room engine

- Start by byte-matching the decode of `rl2wof.pt3` against `tune.com`'s own
  `AYREGS` per tick (instrument both), not by ear.
- Reuse the host integration that now works: flat COM layout, `HEAP_CLEAR` from
  `VARS`, `tune.com` PSG I/O (Z180 slow-I/O bracketing, ROUT bulk writes),
  `PROBETIMER` timer selection. Those are solved; don't relitigate them.
